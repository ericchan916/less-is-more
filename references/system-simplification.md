# 架构减法

关注当前任务的总负担，不按架构流派、文件数或 Agent 数预定结论。把必要结果、当前机制和可用承接者分开。

## 追到实际拥有者

沿相关调用路径确认谁拥有公开契约、规则、已提交事实、未提交草稿、缓存与任务生命周期。接口即使只有一个调用者，也可能承担鉴权、翻译、隔离、取消或错误语义；类型正确和同仓库不能证明这些边界多余。

优先查同一规则多处定义、两个权威互相回写、消费者反复补丁、无职责的纯转发，以及只为旧机制存在的桥接与配置。共享外观不证明共享业务，两个 SQLite 文件也不证明同一职责。

## 找最小的完整承接路径

先核对已有模块、平台或依赖能否接手，再决定保留、合并或替换。对会改变结论的保证查清：

| 保证 | 必须区分的语义 | 可推翻错误替代的检查 |
| --- | --- | --- |
| 去重与重试 | 租户/调用者作用域、请求意图、保留期、首个结果与冲突行为 | 跨租户同键、换参数或窗口外重试，选择当前有关的一项 |
| 持久化与外部副作用 | 本地接受、远端成功和本地确认是否跨越原子边界 | 远端已成功但本地确认前中断，再恢复 |
| 状态与取消 | 显示投影、任务拥有者、停止等待与停止执行的区别 | 取消后查询真正任务与结果，不能只看旋转提示消失 |
| 共享组件与配置 | 互斥模式、独立偏好、不同权限与消费者契约 | 原有合法组合是否仍可完成任务 |

只匹配“支持持久化/幂等”等名称不够。反例失败就保留或补足缺失职责，再继续退役其余已证实的多余设施；不能为少一层丢保证，也不能因一个保证需要保留就保住全部旧框架。

## 副作用恢复的判断边界

持久队列或 outbox 只能证明意图仍在，不能单独证明远端副作用只发生一次。若远端成功后本地尚未确认即中断，恢复可能需要稳定业务标识的状态查询、仍有效的幂等键，或其他已验证的协议。

窗口过期、远端又无法按稳定标识查询时，不能把“未能确认”当成“未发生”。保留不确定状态与人工接手，避免盲目重发；也不能把暂停恢复宣称为完成任务。若用户要求自动完成与不重复两者兼得，先说明协议缺口，不能靠本地多加一张表承诺做到。

需要检查这一边界时，可运行仓库中的隔离 [恢复案例](../evals/architecture-lab/README.md)；它是合成契约与候选实现，不是生产服务或 Agent 优越性测试。

## 退役完整的冗余机制

决定承接路径后，查明哪些转发、同步、配置和消费者补丁因旧机制才存在，把相关项放在同一拟改批次。保留稳定公开契约及真实外部消费者，避免只移除一层却留下维持它的设施。

修复产生者的共同规则可减少下游补丁，但消费者有不同过期、租户或失败语义时不强行合并。独立偏好不要为了消灭布尔值压成互斥模式；没有实际状态替换或隔离需求时，不为组合额外建立 Provider 或依赖注入平台。

比较迁移成本和长期维护成本，必要的短期双路径需有退出条件。复用库可能把成本藏到内部；性能敏感替换使用代表输入验证，普通精简不强制做基准或建立评分体系。

## 验收与输出

用同一任务、输入、权限和相关失败条件比较候选。先看必要契约是否完整，再看重复规则、写入者、同步和维护触点是否真正减少。迁移、数据恢复、并发或真实外部服务未测的部分明确保留未知。

建议通常只需一句决定与关键理由；实施批次再补承接路径和关键验收。不要为每个保留模块或每条原则写一段，也不要通过增加报告、审查角色或模型提示词抵消精简收益。
